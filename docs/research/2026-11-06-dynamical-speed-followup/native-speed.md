# C++動力学カーネルの再調査と性能比較（261106Ch）

## 結論と調査範囲

「既に最適化済みなので高速化の道がない」という結論にはならない。EBSDの非等間隔深さの積分には、計算模型を変えずに指数関数の呼出しを減らせる余地が残っていた。一方、上三角の連続配置と逆数の再利用は、この実装・測定条件では悪化した。数学的な演算数削減だけで採用せず、変更を分けて測った。

対象は正本submoduleの `Crystallography.Native/EigenFuncs.cpp`、`HRTEM.cpp`、`Crystallography/NativeWrapper.cs`、`Crystallography/Diffraction/BetheMethod.cs`。以前のBethe技術基準と今回の総合監査を引き継ぎ、死蔵コードの書換えを実用経路の高速化と数えない。

## 残っていた具体的な費用

EBSDの深さ積分は、固有値を \(\gamma_j\)、深さを \(t\) として、各モード対について

$$
\lambda_{jk}=2\pi i(\gamma_j-\gamma_k^*),\qquad
F_{jk}(t)=\frac{\exp(\lambda_{jk}t)-1}{\lambda_{jk}}
$$

を評価する。小さい \(\lambda t\) の安定な級数は前回監査で既に導入した。

- 調査開始時の非等間隔分岐は、各深さで上三角の全モード対の複素指数関数を呼ぶ。指数関数だけで \(O(TN^2)\) 回になる。
- 等間隔分岐は既に指数の乗算再帰を使っている。そのため、非等間隔で有効な施策を等間隔にも広げてよいとは限らない。
- 等間隔分岐は上三角だけを信号に用いるが、`expAccum` の下三角も更新する。これを省く案は演算数では有利でも、連続したEigen配列演算の効率を失う可能性がある。
- `F` の複素除算は各深さで繰り返される。逆数の事前計算は候補になるが、追加バッファ・分岐・配置を含めた費用を見る必要がある。

また、2026-09-19以降の非局所源モードは、最終的に `background ?? signal` で局所源を置換する。それでも従来の `_EBSDSolverWithTDS` は局所源の `P*C`、`S` と全深さの局所縮約を実行していた。本番経路で捨てる局所源だけを省くことは、非局所の物理模型を変える操作ではない。公開APIの既定の両出力契約は維持する。

## 比較を分けた実験

ローカル `tools/NativeEbsdSpeedStudy` に、現在の2つのEBSDソルバーを凍結し、候補と同一translation unitでコンパイルした。全戦略が同じEigenヘッダー、clang-cl、`/O2 /arch:AVX2 /fp:fast`、ABIを使うので、この差をEigen更新の効果と混同しない。

| 戦略 | 変更内容 |
|---|---|
| Current | 前回の安定積分修正を含む現行実装 |
| PackedReciprocal | 対角→上三角の加算順を保って連続配置し、逆数を事前計算。等間隔の指数更新は使用する対だけ |
| PackedFactorized | 上記に加え、非等間隔深さの指数をモードごとの積へ分解 |
| MinimalFactorized | 旧配置・旧等間隔処理を維持し、非等間隔の指数だけ分解。作業配列は関数内のN要素 |

因数分解は次の恒等式を使う。

$$
u_j(t)=\exp(2\pi i\gamma_jt),\qquad
\exp(\lambda_{jk}t)=u_j(t)u_k(t)^*.
$$

指数関数は \(O(TN)\) 回に減るが、全体のペア縮約は依然 \(O(TN^2)\) であり、上流の固有値分解も消えない。この恒等式は既存ALCHEMI経路でも利用しており、新しい物理近似ではない。

大きい共通の実固有値を先に差し引く。各モードの指数の実部の絶対値が350以下、虚部が1000以下の範囲のみ因数分解を使い、それ以外は元のペア指数へ戻す。別々の増幅・減衰モードを指数化して新たなoverflow/underflowを作ることと、大きい位相を別々にrange reductionする誤差を避ける。`/fp:fast` が `std::isfinite` を省略し得るため、非有限検査にはIEEE-754の整数ビット判定を使う。小さい \(\lambda t\) の級数と、ゼロ深さ・縮退の極限は変更しない。

## 最初のBenchmarkDotNet結果：採用しなかった案も残す

Ryzen 9 9950X、.NET 11 RC3、1 launch / 3 warmup / 8 measurement iterations / 250 ms、Idle優先度、CPU数上限2、MKL/OMP 1 thread。8原子、32深さ。固有値・固有ベクトルは測定外で用意した同じ有限入力を使い、各プロセスのsetupで出力一致を確認した。

| beams | 深さ | 出力 | Current | PackedReciprocal | PackedFactorized |
|---:|---|---|---:|---:|---:|
| 64 | 非等間隔 | 局所 | 1.339 ms | 1.494 ms | 0.352 ms |
| 64 | 非等間隔 | 局所＋非局所 | 1.471 ms | 1.680 ms | 0.460 ms |
| 64 | 等間隔 | 局所 | 0.215 ms | 0.351 ms | 0.337 ms |
| 64 | 等間隔 | 局所＋非局所 | 0.323 ms | 0.492 ms | 0.510 ms |
| 160 | 非等間隔 | 局所 | 8.596 ms | 9.086 ms | 1.717 ms |
| 160 | 非等間隔 | 局所＋非局所 | 10.225 ms | 11.466 ms | 3.618 ms |
| 160 | 等間隔 | 局所 | 1.545 ms | 2.075 ms | 2.071 ms |
| 160 | 等間隔 | 局所＋非局所 | 2.906 ms | 4.114 ms | 4.144 ms |

非等間隔では因数分解込みで約2.83～5.01倍だが、pack/逆数だけでは全条件で悪化し、等間隔では約1.34～1.63倍遅くなった。このためpack/逆数案を本番へ採用せず、非等間隔の因数分解だけを残した最小案へ進んだ。原因を「単に複素除算が速いから」と断定はしない。配置変更、ループのvectorization、チェックとメモリアクセスの費用が同時に変わっている。

最初の数値検証は6,392出力を検査し、全件通過、最大正規化誤差は \(1.93\times10^{-14}\)。0/弱/強吸収、均一/非均一深さ、ゼロ深さ、近縮退、2/7/64/160反射を含み、2波の直接Simpson積分も別に照合した。これは実測試料に対する模型精度の認定ではない。

## 最小案の追跡測定と実装

同じBenchmarkDotNet条件でCurrentとMinimalFactorizedだけを測り直した。前のrunと絶対時間が変わり、ばらつきも大きくなったので、runをまたいだ時間の差を改善効果に含めない。

| beams | 深さ | 出力 | Current | MinimalFactorized | 新/旧時間比 |
|---:|---|---|---:|---:|---:|
| 64 | 非等間隔 | 局所 | 1.970 ms | 0.311 ms | 0.16 |
| 64 | 非等間隔 | 局所＋非局所 | 2.132 ms | 0.424 ms | 0.20 |
| 64 | 等間隔 | 局所 | 0.280 ms | 0.286 ms | 1.03 |
| 64 | 等間隔 | 局所＋非局所 | 0.420 ms | 0.468 ms | 1.12 |
| 160 | 非等間隔 | 局所 | 12.654 ms | 1.718 ms | 0.14 |
| 160 | 非等間隔 | 局所＋非局所 | 14.902 ms | 3.498 ms | 0.24 |
| 160 | 等間隔 | 局所 | 1.923 ms | 1.816 ms | 0.95 |
| 160 | 等間隔 | 局所＋非局所 | 3.804 ms | 3.806 ms | 1.00 |

非等間隔の平均では約4.26～7.36倍。等間隔は0.95～1.12の時間比で区間が重なっており、高速化も完全な無影響も精密には認定しない。最小案は等間隔の指数再帰と加算式を維持し、pack案にあった一貫した大幅悪化は解消した。

最小案を加えた検証は10,540出力で全件通過、最大正規化誤差は同じ \(1.93\times10^{-14}\)。160反射・32原子・128深さの非等間隔条件、空の局所源で局所出力が0かつ非局所出力が不変となる条件も含む。

本番 `EigenFuncs.cpp` へ、非等間隔のモード指数分解、`nAtoms == 0` 時の局所源省略、`tLen == 0` の早期returnを移植した。公開C ABIを変更せず、前回の安定積分helperと今回のEigen更新を保持した。両exportの実行トークンは測定済み最小案と機械照合して一致（追加の空深さguardだけ除外）。旧コードはコメントで残した。本番の全flavorビルド・統合回帰の結果は総合追補に記録する。

この測定は両出力を求めた条件であり、本番の非局所専用モードで局所源を捨てる処理の省略分を、上表の高速化倍率に上乗せしていない。省略の正しさと実際の全工程の時間は別に確認する。

## 他のC++経路と残る候補

- `_CBEDSolver_Eigen` は既に全厚さの伝播を1回のGEMMへまとめている。ここへ同じ提案を再実装する余地はない。固有ベクトルを返すfallbackの `_CBEDSolver_Eigen2` は厚さごとのGEMVだが、標準の全slice経路とは分けて費用を評価する。
- `_STEM_InelasticQ` は既に列packとGEMMタイルでq単位に計算し、4方向の補間と検出器縮約まで1回の呼出しで完結する。古いエントリ単位helperへの置換は退行になる。タイル幅の変更は代表試料のprofileとともに調べる候補であり、根拠なく定数を動かさない。
- EBSDの `EigenSolver → LU → intensity` のnative融合は、固有ベクトルのコピーと一時確保を減らす余地がある。ただし固有値分解の \(O(N^3)\) は残り、任意の吸収背景機能は固有ベクトルをmanaged側でも使う。まず現在の大きい指数関数費用を除いた後で、残る比率を測る。
- `gMap` が恒等写像でも原子位相と非局所源を方向ごとにコピーするC#境界も残る。共有元が読み取り専用で、beamの並びと有効数が同一であることを条件に省略できるが、今回のカーネル結果にその効果を含めていない。
- HRTEMのnative格子ソルバーは位相再帰と256画素ごとの再アンカーを既に持つ。再アンカーを消した見かけの高速化や、使われない旧APIだけの変更は採用しない。

アプリ全体の速度は、EVD・beam選択・ポテンシャル構築・描画を含めた別測定で判断する。今回の測定から、どのEBSD設定でも数倍になるとは主張しない。
